## 2026-09-28 노션형 표 복원 (사용자 화면 승인, 운영 배포 요청)

- 사용자 제공 Notion 다크 테이블을 기준으로 목록을 10열(`계약진행일 / 업체 / 프리 / 가이드 / 선금 금액 / 잔금금액 / 프로젝트 / 특이사항 / 상태 / 입금`)로 변경한다. 상단 출처 탭·처리 단계별 분류·검색·세부 필터·새로고침·30건씩 더 보기는 유지한다.
- 펼치기 전 압축 목록을 제거하고 선금/잔금 원문과 특이사항을 줄바꿈하여 항상 표시한다. 표 본문 14px, 헤더/태그 13px, 상태 12px, 어두운 배경과 얇은 구분선, 표 내부 가로/세로 스크롤과 고정 헤더를 적용한다. 고객 레코드는 테스트에 사용하지 않는다.

- 운영 잔금 원장도 같은 표 컴포넌트를 사용하되 기존 중도금을 보존한 11열이다. 업체 열에서 프로젝트와 계약일을 독립 열로 이동하고, 기존 회차 편집·추가 모달, 특이사항 추가/수정/삭제, 보관/복원, 고객 상세, 요청/입금 상태 저장 핸들러를 유지한다. 상태 선택은 표 스크롤에 메뉴가 잘리지 않도록 네이티브 select로 변경한다.
- 변경 범위는 프런트 표시 코드·합성 테스트·문서다. API·Auth·DB·노션 수집·Sheets 백업·금액 계산·집계·저장 로직은 변경하지 않았다. 노션 자료는 계속 읽기 전용이다.

## 2026-09-24 상태별 화면 재구성 (운영 배포 완료, 아래는 이전 화면 기록)

- 기존 10열 원문 표 대신 `전체 / 지급요청 전 / 요청 진행 / 입금 대기 / 입금 완료 / 상태 확인` 단계별 건수와 압축 목록을 제공한다. 각 행을 펼치면 선금·잔금·프로젝트·특이사항·원문 상태와 노션 링크를 모두 확인할 수 있다. 최초 30건을 표시하고 `더 보기`로 추가한다.
- 분류는 읽기 시점의 표시 계산만 수행한다. `입금완료`·`카결완료`는 입금 완료, `입금전 + 완료`는 **입금 대기**, `입금전 + 지급요청1/2/3`은 요청 진행, `입금전 + 지급요청 전`은 지급요청 전이다. 그 밖의 상태는 확인 필요로 남긴다. 요청 완료만으로 입금 완료를 추정하지 않는다.
- 2026-09-24 운영 DB의 상태 조합 건수(업체명·메모 미조회): 전체 194, 지급요청 전 51, 요청 진행 15, 입금 대기 120, 입금 완료 8, 상태 확인 0. 단계별 합계는 전체와 같다.
- 원문 금액을 숫자로 바꾸거나 운영 결제 원장과 자동 매칭하지 않는다. 기존 직원 인증 API·Supabase 테이블·노션 수집·Google Sheets 백업·계약/수금/미수 집계는 변경하지 않는다.

## 화면과 금액 경계

- `잔금 관리 > 운영 잔금 원장`은 기존 계약·결제 회차·실입금의 운영 정본이다.
- `잔금 관리 > 노션 이관 자료`는 별도 읽기 전용 참고 목록이다. `source_key`별로 업체, 계약진행일, 프리, 프로젝트, 선금·잔금 **원문**, 요청 상태, 입금 상태, 특이사항, 노션 원본 링크를 보여준다.
- 노션 선금·잔금은 자유 텍스트이므로 통화 숫자나 입금일로 추정하지 않는다. 원본에 없는 금액은 `—`로 표시하며 0원으로 바꾸지 않는다. 이 목록은 계약액·입금액·미수금·ROAS 및 기존 15분 Sheets 백업에 합산·투영하지 않는다.
- 노션 `요청 상태=완료`와 `입금 상태=입금전`이 동시에 존재한다. 운영 Supabase에서 해당 조합 120건을 확인했으므로 요청 완료를 수금 완료로 취급하지 않는다. 전체 194건 중 업체명 미입력 2건, 계약진행일 미입력 70건, 잔금 원문 미입력 63건이다.
- 회사명만으로 기존 고객과 자동 병합하지 않는다. 후속 통합은 노션 페이지 ID와 계약/업체 고유 ID의 검증된 1:1 매칭, 텍스트 금액의 수동 검수, 입금 증빙을 거친 뒤 별도 승인받는다.

## 보안·API

- 브라우저는 기존 Supabase 직원 세션으로 `kpi-domain-api?action=notion_receivables`만 호출한다. 서버는 활성 조직 membership을 확인하고 `organization_id`로 범위를 좁혀 페이지 단위로 읽는다.
- API는 화면에 필요한 열만 선택하며 `raw_payload`를 보내지 않는다. 직접 브라우저 테이블 접근은 허용하지 않는다. 이관 테이블에 기존 부여돼 있던 `anon`/`authenticated`의 부수 권한도 해당 표에서만 회수한다. 서비스 역할의 기존 이관 권한은 유지한다.
- 조회 실패 시 기존 결제 원장은 유지하고, 마지막 조회 목록이 있으면 그것을 유지하면서 오류를 보여준다. 미로그인·권한 없는 사용자는 기존 앱 진입 및 API 경계에서 차단된다.
- 노션 원본은 별도 이관 프로세스가 갱신한다. 이 화면의 새로고침은 **Supabase 조회만** 수행하며 노션 수집을 실행하지 않는다. 목록의 최종 반영 시각은 DB `updated_at` 중 최댓값이다.
