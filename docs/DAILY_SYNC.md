# 프리미팅·계약 시트 일일 동기화

기준: 2026-09-15, Asia/Seoul. 운영 정본은 KPI Supabase이며 Google Sheets로 후퇴하여 저장하지 않는다.

## 사용자 동작과 실행 범위

| 동작 | 원천·처리 | 범위 |
|---|---|---|
| 프리미팅 동기화 | CRM 캘린더 `mr_schedules`, `mr_type=1`. 방문 확인 전에도 업체 생성, 확인 후 완료 정보 보완 | 실행일 포함 최근 3일(D-2~D), 미래 제외. 화면에서 선택한 달과 무관 |
| 시트 동기화 | 계약 프로세스 시트의 신규 계약과 기존 프리미팅 기업 1:1 매칭, 계약액·내용 자동 보완 | 기존 계약 정책인 2026-08-01~오늘 유지. 3일 제한은 캘린더에만 적용 |
| 자동 실행 | 프리미팅 → 시트 순서. 한쪽 실패해도 다른 쪽 시도 | 한국시간 매일 09시 이후 1회, 페이지를 닫아도 실행 |

- 9/15 실행 범위는 9/13~9/15. `생성일`이 아니라 **캘린더 일정 시작일** 기준이다.
- 프리미팅 수(일정 건수)와 업체 수는 다를 수 있다. 한 업체의 여러 일정은 `crmMeetings`에 각각 저장한다.
- 날짜가 범위 밖인 과거 일정은 재조회·재작성하지 않는다. 이미 보관된 과거 기록은 삭제하지 않는다. 3일보다 오래된 일정에 늦게 내방 체크하면 이 작업에 포함되지 않는 제약이 있다.
- 프리미팅 버튼은 오늘 성공했어도 사용자가 누르면 재확인한다. 최초 요청의 일회성 최신화와 예약 작업은 당일 같은 범위 성공 기록이 있으면 재조회하지 않을 수 있다.
- 계약 시트에서 신규·미등록인 업체는 기존 `신규업체 생성 / 제외` 큐를 유지하며 무조건 생성하지 않는다. [계약 반영 규칙](CONTRACT_AUTO_SYNC.md).

## 일정·장애 처리

- `crm_lead.gs`의 `runPocketDailySync`를 5분마다 깨우는 Apps Script 트리거 **1개**. 이는 5분마다 CRM을 수집한다는 뜻이 아니다. 시간·날짜 조건만 검사하고 하루 실제 작업은 1회다.
- 최초 활성일 **2026-09-16**. Apps Script 예약 특성상 09:00 정각 보장이 아니라 그 이후 첫 실행이다.
- ScriptLock으로 동시 실행을 막고 `KPI_DAILY_ATTEMPT_DAY`를 작업 전에 기록한다. 부분 실패·응답 불명확 시 그날 무한 자동 재시도를 하지 않는다. 수동 버튼으로 재확인할 수 있다.
- 성공·실패·최종 범위·건수·리비전은 Script Properties의 `KPI_SYNC_premeeting`, `KPI_SYNC_sheet`, `KPI_SYNC_daily`에 소형 운영 상태로 보관한다. **업체·계약 데이터의 저장소는 이 속성이 아니라 Supabase**다.
- 화면은 1분마다 상태만 조회한다. 새로운 성공 결과가 있으면 Supabase 최신 정본을 재조회하고 로컬 미저장 입력을 보존한다. 서버 결과의 오래된 스냅샷을 화면에 주입하지 않는다.
- 상태 조회/화면 갱신 실패 시 성공으로 꾸미지 않고 오류 표시. Apps Script 응답 리다이렉트에서 간헐적 404가 발생한 사례가 있어, 멱등성이 검증된 세 동기화/상태 액션에 한해 전송 실패를 1회 재시도한다. 다른 쓰기·업무 오류는 임의 재시도하지 않는다.
- 자동 실행 실패는 `pocket_daily_sync_failed`로 기록하여 Apps Script 트리거 실패로도 남긴다. 별도 신규 이메일 서비스는 추가하지 않았다.

## 데이터 보호와 연동

1. Apps Script가 기존 Supabase Edge CRM 수집 경로를 사용한다. 신규 직접 CRM 조회를 추가했다가 구형 Script Property 토큰의 401을 발견해 제거했다. Edge의 현재 서버 인증정보가 우선이다.
2. CRM 고객 ID·프로젝트 ID·일정 ID로 매칭하며 식별자 충돌은 보류한다. 이름만 같은 서로 다른 CRM 고객을 임의 합치지 않는다. 보관 처리된 고객을 되살리지 않는다.
3. Supabase 최신 리비전으로 필요한 필드 패치만 만든다. 충돌 시 최신 상태로 최대 3번 다시 계산한다. 같은 일정 재확인은 패치·로그를 중복 생성하지 않는다.
4. 기존 계약액·계약일·입금·결제회차·잔금·사용자 메모를 캘린더가 수정하지 않는다. 기존 일정 이력도 유지한다. 추가/변경과 활동 로그는 같은 저장에 들어간다.
5. 기존 브라우저 유입 DB·TM 품질 갱신에서 별도 60일 캘린더 병합과 `firstVisitAt`만으로 프리미팅을 만드는 처리를 제거했다. 프리미팅 생성은 전용 서버 경로가 담당한다. 유입·품질 조회 자체와 명시적 업체 단건 가져오기는 유지한다.
6. 기존 광고 수집·Supabase 저장·Sheets 백업은 유지한다. 설치 과정에서 옛 `syncPremeetings` 트리거와 같은 일일 핸들러 중복만 제거한다.

## 코드·검증

- 순수 로직: `scripts/premeeting-sync-core.mjs`.
- 런타임: `scripts/daily-sync-runtime.gs`.
- 생성: `node scripts/build-premeeting-sync.mjs` → `../pocket-kpi-deploy/crm_lead.gs`. 별도 4번째 GS 파일을 사용자에게 추가하라고 요구하지 않는다.
- 라우트: `Code.gs`의 `premeeting_sync`, `contract_auto_sync`, `daily_sync_status`. 트리거 최초 설치는 공개 앱 토큰과 별개인 1회용 비밀값 SHA-256 확인 후 사용 완료 처리한다. 원본 비밀값은 공개 Git·빌드에 포함하지 않는다.
- 운영 Apps Script **버전 58**, backend `2026-09-15-daily-sync-v28`. 같은 웹 앱 URL 유지.
- 실제 9/13~9/15 일정 **5건(완료 4, 예정 1)**, 추가 0·수정 0·보류 0. 오늘 이미 DB와 일치하므로 업무 데이터 재반영 없음. 9/15 17:39 KST 성공 확인 상태만 기록.
- DB 전후 **776개** 동일, 리비전 `20260915080053524-54mg` 동일. 모든 기존 업체 및 금액·결제·메모 불변 확인.
- 당일 계약 시트 12곳 반영은 이전 작업에서 검증 완료했으므로 이번에 재실행하지 않았다. 신규 일일 상태의 `sheet:null`은 새 기록이 아직 없다는 뜻이지 기존 저장 실패라는 뜻은 아니다.
- `triggerCount=1`, `enabledFrom=2026-09-16` 실응답 확인. 첫 예약 실행은 아직 미래이므로 이미 실행 성공했다고 주장하지 않는다.
- 단위 테스트 83개 및 프로덕션 빌드 통과. 격리 브라우저에서 버튼·550만원 반영·보류 사유·실패 표시·데스크톱/모바일 검증. 운영 입력을 테스트용으로 추가하지 않았다.
- 운영 검증 자료는 git-ignored `artifacts/daily-sync-backup/`. 원시 고객 데이터·OAuth·설치 비밀값은 공개 저장소에 업로드하지 않는다.

## 롤백

UI만 되돌려도 이미 등록된 트리거는 남는다. 필요 시 해당 프로젝트의 `removeDailyTrigger`로 이 작업의 두 핸들러만 제거하고, 검증한 이전 Code/crm_lead 버전을 복원한다. 광고·백업 트리거를 일괄 삭제하지 않는다. 업무 데이터는 전체 스냅샷 덮어쓰기가 아니라 최신 값과 대조한 역패치로만 복구한다.
